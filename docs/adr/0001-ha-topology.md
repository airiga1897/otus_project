# ADR 0001. Балансировка и отказоустойчивость CMS

**Статус** — принято для учебного стенда.

## Контекст

Задание требует кластеризацию и балансировку веб-сервера и СУБД. CMS должна продолжать запись при потере реплики, а при отказе primary запись должна восстановиться автоматически. Три голоса Consul размещаются на разных ВМ в пределах стенда из пяти узлов.

## Решение

- На каждом веб-узле работает HAProxy для веб-трафика и локального доступа Django к БД. Облачный балансировщик проверяет доступность обоих входных HAProxy.
- В PostgreSQL два узла с асинхронной потоковой репликацией. Patroni координирует автоматическое переключение через Consul как единственный DCS.
- HAProxy определяет RW-узел по Patroni `/primary`. Пул RO включает primary и пригодную реплику. Проверка реплики учитывает согласованный предел отставания. Django направляет в RO только операции, допускающие устаревшие данные. Запись и немедленное чтение её результата используют RW.
- Consul также обслуживает обнаружение сервисов через внутренний DNS. Роль PostgreSQL для маршрутизации HAProxy определяется проверками Patroni.
- После отказа и возврата реплики Patroni возобновляет потоковую репликацию при наличии нужных WAL. Возврат бывшего primary после переключения проверяется отдельно. Предусмотреть `pg_rewind` при выполненных предпосылках и процедуру пересоздания при необходимости.

## Последствия и проверка

При отказе primary могут потеряться подтверждённые записи, WAL которых ещё не дошли до реплики. При отказе одной ВМ БД остаётся одна копия данных до восстановления второй. Один оставшийся веб-узел должен выдерживать нагрузку испытания. Проверки описаны в [сценариях защиты](../acceptance.md).
