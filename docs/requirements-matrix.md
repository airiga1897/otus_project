# Требования и источники

## Критерии приемки

| Требование | Реализация в плане | Подтверждение |
|---|---|---|
| Облачный Terraform и автоматизация конфигурации | Terraform и Salt | Развёртывание и повторный прогон |
| Минимум два веб-сервера и балансировка | Два Django/Gunicorn и два HAProxy за облачным балансировщиком | Запросы к обоим узлам и потеря каждой веб-ВМ |
| Минимум две СУБД, кластеризация и балансировка | PostgreSQL, асинхронная репликация, Patroni, Consul, HAProxy RW/RO | Проверка распределения чтения и отказов обеих ролей |
| Межсетевой экран с запретом по умолчанию | Облачная фильтрация и перечень разрешённых потоков | Положительные и отрицательные сетевые проверки |
| Скрипты резервного копирования | Запуск с ops-01, копии в объектном хранилище | Восстановление в отдельную БД |
| Центральный ELK | Агенты сбора, Logstash, Elasticsearch, Kibana | Логи двух веб-узлов и события отказа |
| Prometheus | Метрики веба, PostgreSQL, HAProxy и Consul, Alertmanager | Графики и оповещения в испытаниях |

## Требования Django

Статус строк — запланировано или обусловлено выбранным контрактом. Идентификаторы соответствуют исходному REQUIREMENTS.md.

| ID | Применение и подтверждение |
|---|---|
| A1–A10 | Сервисы для бизнес-логики, repository для сложного и сменного доступа, один DTO на контракт. Типизация публичных интерфейсов и mypy со stubs. DRY, проверка Windows/dev и Linux/CI/prod, обзор переиспользования и ADR. Миксины по потребности. Celery при наличии отдельной задачи. |
| P1–P7 | При наличии API — версия в URL, dev-only browseable/root API с базовой авторизацией, RFC 7807, пагинация, фильтрация и сортировка, генерация OpenAPI для Swagger/ReDoc. Проверка схемы в CI желательна. Контракт API определить при выборе функций CMS. |
| S1–S8 | Явный контракт Django sessions для веба и JWT при соответствующем API-контракте. Раздельные лимиты для анонимных и авторизованных, лимиты размера глобально и на endpoint, CSP, валидируемые поля, логи без чувствительных данных, секреты из окружения. |
| S9–S12 | При наличии tenant-данных ограничивать queryset владельцем. Рассмотреть Argon2 и аудит зависимостей и секретов. Пользовательский HTML санитизировать при его отображении. |
| C1–C9 | Logging вместо print, явные исключения, типизированные вариативные аргументы, McCabe до 10 либо обоснование, предсказуемый naming, Ruff и форматтер, инициализация вне импорта. Русские пояснения по возможности. Сохранять строгость mypy. |
| T1–T8 | Тесты каждого приложения, TDD для критичных операций, фактический вход в интеграционных тестах, factory_boy, проверка идемпотентности применимых методов и покрытие критической логики не ниже 95%. force_authenticate только в unit-тестах ViewSet. Рассмотреть strict pytest, мутации и шардирование по применимости. |
| R1–R8 | Явная обработка отказов, liveness/readiness, идемпотент-ключи для критичных обновлений по контракту, отдельные ENVIRONMENT и DEBUG, Gunicorn. JSON stdout для ELK, единая env-конфигурация. Sentry и WhiteNoise по необходимости. |
| D1–D11 | Env/stdout, отдельный шаг миграций с проверкой совместимости. Ruff, mypy, pytest, drift миграций и проверка Poetry lock в CI. Локальный gate с отчётом. Сборка, аудит, публикация образа, передача digest на этап развёртывания через Salt. IPv4-first. Deploy check, smoke и merge-conflict hook по применимости. |
| O1–O6 | Владельцы критичных путей, PR-шаблон, проверки в каждом PR, ветвление от согласованной базы. Рабочая база проекта — otusproject01. Перед закрытием сверять требования и результаты. |
| AI1–AI5 | Применимость появится при включении FastAPI, Celery или LLM-сервиса. В текущей архитектуре таких компонентов нет. |
